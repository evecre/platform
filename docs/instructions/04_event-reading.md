## 0. 背景

一覧と詳細が本番 API につながり、公開されたイベントが見られる状態になった。ここから先は**読み物としての質**の作業に入る。

このサイトの目的は、イベクリで作られたイベントの**制作の裏側・ナレッジ**を、そのイベントを知らない人（次の代の学生、他の団体）が読んで役に立つ形で見せること。参考にしているのは次の3つのメディアで、1エントリあたりのメタデータが揃っていること、分類が固定されていることが共通点になっている。

- `https://mount.jp/magazine/` … 6分類。特に「制作の裏側」を「つくり手が素直に話す、苦労話やあの時の感情とできごと」と定義している
- `https://necco.inc/note/` … サムネイル＋タイトル＋著者＋日付＋カテゴリ。記事総数を出している
- `https://goodpatch.com/blog`

**イベクリの場合、記事の中身にあたるのは「引き継ぎ書」**であって、ストーリーや対談ではない。行った策・その結果・つまずいた点が並ぶ。だから見た目は編集的に、中身は報告書として読める形にする。

### ★「つまずいた記録」を主役にする

いまの詳細ページは、振り返りを `outcome` によってラベルだけ出し分けている（`REVIEW_LABELS`）。**この `outcome` は、このサイトでいちばん価値のある情報**なのに表示されていない。

mount が「制作の裏側＝苦労話」と定義しているのと同じで、**読む人がいちばん知りたいのは、どこで詰まったか**。隠す情報ではなく、見出しに出す情報として扱う。

## 3. ナレッジの見せ方

### 3-0. JS の目印を `data-*` に付け替える（§3・§4 と同時に）

いまのコードは、カードとナレッジ1件の中身を**見た目用のクラス名で探している**。

- `assets/js/pages/event-log.js`（`buildCard`）… `.c-event-card__thumb` / `__label` / `__title` / `__date` / `__venue`
- `assets/js/pages/event-detail.js`（`buildKnowledge`）… `.p-event-knowledge__title` / `__tags` / `__text` / `__images` / `__files`

このあと見た目を作り込む段階に入るので、クラス名を変えた瞬間に**表示が無言で壊れる**。§3・§4 でこの2つのテンプレートを組み直すので、そのときに付け替える。

- `data-card="title"` / `data-knowledge="title"` のような `data-*` にする
- ナレッジのテンプレートは**すでに `data-knowledge="firstLabel"` / `"struggle"` / `"solution"` を使っている**。新しい規則ではなく、始まっているパターンを完成させる作業になる
- クラスは**見た目のためだけ**に残す
- ★**この2つのテンプレートの中だけ**にすること。他のファイルを掃除しに行かない
- `assets/css/README.md` の §5（「このクラスは消さないこと」の記述）も合わせて直す

### 3-1. `outcome` を出す

`knowledge[].outcome` は `"success" | "struggle" | null` で届いている。いまはラベルの出し分けにだけ使われていて、表示されていない。

- 各エントリ（`.p-event-knowledge`）の**タイトルの近くに、判定を1つ出す**
  - `success` → 「うまくいった」
  - `struggle` と `null` → 「つまずいた」
- ★`null` を「つまずいた」として扱うのは、既存の `REVIEW_LABELS` の分け方と同じ（`item.outcome === 'success' ? 'success' : 'struggle'`）。**判定の分け方を2か所に書かないこと。** 1つの関数にまとめて両方から呼ぶ
- 色は `success` と `struggle` で変える。ただし **`struggle` を警告の色（赤系）にしないこと。** つまずいた記録はこのサイトでいちばん読まれる情報で、悪いものとして見せない。両方とも落ち着いた色で、区別がつく程度にする
- 文言は `event-detail.js` の1か所にまとめる（`REVIEW_LABELS` の隣）

### 3-2. エントリのメタデータを揃える

いまのエントリは「タイトル → タグ → 振り返り → 本文 → 画像 → ファイル」の順。参考サイトの型（タイトル・分類・日付）に寄せて、**読む前に何の記録か分かる**形にする。

- エントリの頭を **タイトル ＋ 判定 ＋ タグ** の1ブロックにまとめる
- 振り返り（困ったこと／次にやるなら）を**本文より先**に置く。いまもその順になっているので、見た目の区切りを強くするだけ
  - ★この順番を変えないこと。本文（何をしたか）より振り返り（何が起きたか・次どうするか）のほうが、知らない人には先に要る
- 本文・画像・ファイルは「詳しく」のまとまりとして、少し引いた見た目にする
- ★日付は `knowledge[]` に入っていない（API に完了日が無い）。**出さないこと。** 無いものを推測して出さない

### 3-3. 読み物としての組み直し

- エントリの間に十分な余白を取り、1件ずつ読めるようにする。カードで囲むかどうかは任せる（囲まないほうが通読しやすい）
- `.p-event-detail__summary`（概要）を、タイトル直後のリードとして強めに見せる
- ナレッジの節の前に、**何件あるか**を出す（§4 と同じ考え方）
- 画像は既存のとおり `loading="lazy"` と、読めないときに枠ごと外す処理を維持する

## 5. 「つまずいたこと」の横断索引

**このサイトでいちばん価値が出る場所**だと考えている。全イベントの「つまずいた記録」を1ページに集め、他団体の学生が自分の困りごとから探せるようにする。本体の展示で予定している「困ったことめくり」のデジタル版にあたる。

### 作るもの

`pages/event-log/struggles/`（パスは任せる。`pages/event-log/` の下に置くこと）

- 全イベントの `knowledge[]` から **`outcome !== 'success'` かつ `solution` が空でない**ものを集めて並べる
- 1件の表示：**困ったこと → 次にやるなら**、そして出どころ（イベント名・タスクのタグ）。イベント名は詳細ページへのリンクにする
- **タグ（企画／運営／制作／広報）で絞り込めるようにする。** 一覧の `[data-filter]` と同じ作りを流用する
- 一覧ページとイベント詳細ページから、このページへの導線を1つずつ置く

### ★取り方の制約（ここを守らないと API に断られる）

一覧（`GET /api/public/events`）には `knowledge` が**含まれない**。詳細を1件ずつ取る必要がある。公開 API は **1分 60回／IP** で、超えると 429 を返す。

- **`hasKnowledge === true` のイベントだけ**詳細を取る（一覧に入っている）
- **多くても 20 件まで**。それを超えるときは、`dates` の最終日が新しい順に 20 件だけ取り、ページの下に「新しい20件から集めています」と出す
- **順に取る**（並列で投げない）。`api.js` の `getEvent()` をそのまま使えば `sessionStorage` のキャッシュも効く
- **途中で失敗しても、取れた分だけ出す**。`RateLimitedError` が出たらその時点で止めて、取れた分＋「ただいま混み合っています」を出す
- 読み込み中は進捗が分かるようにする（件数でよい）
- 展示モード（`?kiosk=1`）では `api.js` が snapshot を先に見るので、`npm run snapshot` を取っておけば API を叩かずに出る

### 報告してほしいこと

イベントの件数が増えると、この取り方は破綻する（20件の制限が効き始める）。**本体側に「全イベントの振り返りをまとめて返すエンドポイント」を足すべき時期**が来るので、実装したうえで「何件まで実用的か」を報告に書くこと。

## 8. ★本体側に確認が必要なこと（実装の前に報告すること）

**見出しと箇条書きが、このサイトでは平文になる見込み。**

本体の指示書Bで、タスクの本文に**見出し**と**箇条書き**の書式が入る。本体の中では `{{h}}…{{/h}}` / `{{l}}…{{/l}}` という印で保存され、画面上は見出し・箇条書きとして描かれる。

ところが本体の `lib/publicData.js` は、公開 API に出すときに**印を外して文字だけを残す**（いまも太字・斜体の印 `{{b}}` / `{{i}}` が同じように外されている）。つまり：

- **見出しは、ただの1行になって本文に埋もれる**
- **箇条書きは、行頭の点が無い行の連なりになる**

このサイトの目的（読み物として見せる）に対して、**見出しが失われるのがいちばん痛い**。

### 提案（本体側に足してもらう必要がある）

`knowledge[]` の各件に、構造を解いた配列を1つ足してもらう。

```json
{
  "title": "ポスターを作る",
  "text": "初稿を共有\n…",
  "blocks": [
    { "type": "heading", "text": "決めたこと" },
    { "type": "text",    "text": "3案を並べてメンバーで投票した" },
    { "type": "item",    "text": "入稿は前日まで" },
    { "type": "item",    "text": "サイズは A2" }
  ]
}
```

- `text` は**いまのまま残す**（平文・後方互換）。`blocks` が増えるだけなので契約は壊れない
- **印の解釈をこのサイトに持たせないこと。** 本体が構造を解いて渡す形にする。印の仕様を2つのリポジトリに分散させると、本体が印を変えたときにこのサイトだけ壊れる
- サイト側は `blocks` があればそれで描き、無ければ `text` を使う

### このフェーズでの扱い

- **`blocks` を見る実装は、まだ作らない**（来ていないので）
- 代わりに、**`text` を描いているところを1か所にまとめておく**（`buildKnowledge` の `setTextOrRemove(q('.p-event-knowledge__text'), item.text)` のあたり）。あとで `blocks` に差し替えやすくしておく
- この §8 の内容を**報告に書き、`docs/api-contract.md` に「本体へ依頼中」として記録する**
